## Measured latency

Median **microseconds per matrix multiplication**; lower is better. `matmul` below denotes naive row-major `i-j-k` loops for Goose and C; BLAS columns both call **OpenBLAS SGEMM**.

| Shape | Goose naive | C naive | Goose → OpenBLAS | C → OpenBLAS | NumPy | PyTorch CPU |
|---|---:|---:|---:|---:|---:|---:|
| 32×32 | 34.207 | 20.278 | **2.458** | **1.653** | 4.228 | 4.361 |
| 64×64 | 353.011 | 148.473 | **10.931** | **9.072** | 10.720 | 11.656 |
| 128×128 | 3,514.971 | 2,617.862 | **73.727** | **56.636** | 55.534 | 56.967 |

## Interpretation

1. **Goose → OpenBLAS is working**, including the Goose/C ABI adapter, row-major layout, and linking on Linux. The central numerical result is that Goose achieves access to an optimized CPU GEMM backend, not that its naive GEMM now accelerates by itself.
2. The Goose BLAS wrapper is slower than direct CBLAS in all three selected sizes. At 128×128 this is about 30% more elapsed time; at 32×32 the absolute median gap is 0.805 µs. However, three measurements on a shared runner do not isolate FFI overhead from host noise and differing call-site optimization. **Treat this as an optimization target, not as a conclusive FFI cost estimate.**
3. NumPy and PyTorch matrix multiplication show similar magnitude to optimized CBLAS for 64×64 and 128×128, consistent with using highly optimized native tensor libraries.
4. A later controlled experiment should use repeated inner-loop operations, more trials, CPU pinning, consistent input residency, and analysis of compiled Goose-generated C. The C comparator calls CBLAS directly; the Goose implementation performs public API shape assertions and then enters a dedicated C adapter. An adapter-matched C control is required to distinguish validation costs from language/ABI costs.
5. The checksum checks are aggregate and allow tolerances. Independent per-output numerical tests are still required across varied shapes.
